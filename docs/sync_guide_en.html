Data Sync Guide v2

Terrain sprites, new types, and custom map terrain — all without rebuilding the app.

This guide covers the full runtime data pipeline between MapEditorPro and the Unity mobile app. Three previous limitations have been removed:

LimitationStatus
Synced sprites lost on app restartFixed — saved to device storage, loaded on startup
New terrain types require a code rebuildFixed — registered as dynamic tiles at runtime
Custom terrain types can't be used in mapsFixed — Map Editor exports custom_terrain, Unity reads it back

How It Works

Workflow: Update Sprites for Existing Terrain

Use this when you want to change the look of a terrain type that already exists in the app (one of the 29 built-in types).

  1. In MapEditorPro → HexDB, find the entry whose id matches the terrain's Unity ID (e.g. rubble_1). Set its Sprite Name to the filename of your new PNG (without extension).

  2. Export hex_database.json via File → Save Hex DB.

  3. Upload the new PNG(s) and the updated hex_database.json to the shared Google Drive folder. Replace existing files when prompted.

  4. In the app, open the Maps panel and tap Sync Database. The sprite updates immediately and the map redraws.

  5. On the next app start, the updated sprites load from device cache — no network call needed.

Instant + persistent. The update applies live to the running session and survives restarts. No rebuild, no redeploy.

Workflow: Add a Brand-New Terrain Type

Use this when you need a terrain type that doesn't exist in the current build — e.g. Volcanic Ash, Frozen Lake, etc.

  1. In MapEditorPro → HexDB, click + Add Hex. Give it a unique string Id that does NOT match any built-in terrain name (the 29 names like Plain_1, Rubble_2, etc.).

    The Id is your permanent string key. Once tiles or maps use it, don't rename it. The Type field is optional for custom types — leave it blank or set a close enum equivalent for game-logic fallback (e.g. Plain_1 for buildability).

  2. Set Sprite Name to the filename of your terrain PNG (without extension, e.g. hex_volcanic_ash).

  3. Export hex_database.json and place the PNG in the export folder.

  4. Upload both to Google Drive.

  5. In the app, tap Sync Database. Because the ID doesn't match any compiled TerrainTypeDefinition, the app calls RegisterDynamicTile — the tile is added to the runtime dictionary and renders with your custom sprite.

  6. On next app restart, the tile is restored from device cache automatically — no re-sync needed unless you update the sprite.

Game-logic properties (IsBuildable, ExplorationCost) are not set for dynamic types. They default to buildable/cost=1. To change these properties you still need to add the type to the TerrainType enum and run PostApoc → Import Hex Database in the Unity Editor — but visual rendering works fully at runtime.

Workflow: Use Custom Terrain in Maps

Paint your custom terrain type onto a map in the editor and have the Unity app apply it correctly.

  1. Complete the Add New Terrain Type workflow first — the custom type must already be synced to the app before a map using it is applied.

  2. In MapEditorPro, open the terrain palette. Custom HexDB types appear below the 29 built-in types as additional palette buttons showing your sprite (or a fallback icon).

    If the palette was open before you added the HexDB entry, reload the page to refresh it. Custom buttons appear automatically when HexDB has entries whose IDs don't match any built-in terrain name.

  3. Click your custom terrain button to select it, then paint normally. The cell stores Plain_1 as the visual fallback in the int grid and your custom ID in a parallel overlay — the editor renders your sprite on canvas.

  4. Export the map via File → Export Map JSON. The exported JSON includes a custom_terrain array listing every cell that uses a custom type:

    {
      "width": 50, "height": 50,
      "data": [[12,12,9, ...]],
      "custom_terrain": [
        { "x": 5, "y": 3, "id": "volcanic_ash" },
        { "x": 6, "y": 3, "id": "volcanic_ash" }
      ]
    }

    Old map JSONs without custom_terrain continue to work — the field is optional.

  5. Upload the map JSON to Google Drive alongside the existing maps.

  6. In the app, open the Maps panel, tap your map to download and apply it. RuntimeMapApplier processes the custom_terrain array: each cell gets TileData.CustomTerrainId set to the string ID. TileRenderer renders it using the dynamic tile registered in step 1's sync.

  7. The custom terrain IDs are saved to the save file. On the next session start, MapManager restores them before the first render — your map looks correct immediately without re-downloading the map JSON.

Undo/Redo works. The Map Editor's History system snapshots both the terrain grid and the custom overlay together — undoing a custom terrain stroke removes it from the export correctly.

Persistence & Cache

After a successful sync, files are saved to device storage:

📁 Application.persistentDataPath/HexCache/
  📄 hex_database.json auto-saved
  🖼 hex_plain_1.png auto-saved
  🖼 hex_volcanic_ash.png auto-saved
  🖼 ...

Startup sequence

  1. RuntimeDatabaseSync.Awake() runs → LoadFromCache() reads HexCache from disk and registers all tiles into TileRenderer. No network call.

  2. MapManager.LoadFromSave() runs → restores CustomTerrainId on tiles from the save file.

  3. RebuildVisuals() renders the map — all custom tiles display correctly because cache was applied before the render.

Remaining Limits

Game-logic properties need a code rebuild

IsBuildable, ExplorationCost, tap cost calculations — these come from TerrainTypeDefinition ScriptableObjects which are compiled into the build. To set them for a new terrain type you still need to:

  1. Add the value to the TerrainType enum in TerrainTypeDefinition.cs
  2. Run PostApoc → Import Hex Database in the Unity Editor
  3. Build and redeploy the APK

Visual rendering (sprite) works at runtime for all types. Game logic only needs a rebuild for new types.

Dynamic tiles are in memory only between syncs

The Tile ScriptableObjects created at runtime are not saved as Unity assets — they exist in memory for the session. They are re-created from the cache file on every cold start, so visually they are always present. But if you clear the app's storage (Settings → Clear Data), the cache is lost and a re-sync is needed.

Pixels-per-unit must match your sprites

The Pixels Per Unit field on RuntimeDatabaseSync defaults to 100. If your hex sprites were authored at a different resolution (e.g. the existing tiles use 64 PPU), set this field to match. All downloaded sprites use the same PPU value.
